# knowledge リポジトリ利用ルール

プロジェクト横断で再利用可能な開発ナレッジの置き場。主読者は LLM エージェント（特定ツールに限らない）。
ツール固有のワークフローはここに書かず、各ツールの設定ファイルに置く。このファイルはツール非依存の規約のみを持つ。

## 読み方

1. まず [README.md](README.md) の索引（1行/1ノート）を読み、必要なノートだけ開く
2. キーワードで探すときは索引と frontmatter の `description` を grep する
3. 全ノートの一括読み込みはしない（トークン浪費）

## 書き方

### 配置

| ディレクトリ | 内容 | 例 |
|---|---|---|
| `patterns/` | 実装パターン・スニペット | 検証手法、エラーハンドリング様式 |
| `decisions/` | 横断的な技術選定の結論と理由 | ランタイム選定、ツールの使い分け基準 |
| `runbooks/` | 手順・チェックリスト | リリース手順、環境構築 |

### ノート形式

- 1トピック1ファイル。ファイル名は kebab-case（`^[a-z0-9]+(-[a-z0-9]+)*\.md$`）
- frontmatter 必須。`name` はファイル名（拡張子なし）と一致させる

```markdown
---
name: example-note
description: 索引・grep で発見されるための1行要約（結論を書く）
tags: [testing, terminal]
---

本文。結論を先頭に。経緯・根拠は後ろに。
```

### 書き込み手順

1. **既存確認が先**: 同じトピックのノートがあれば新規作成せず更新する
2. ノート作成・更新したら README.md の索引に1行追記（`- [タイトル](path.md) — フック`）。索引とファイルの整合は pre-commit で機械検査される
3. 相対日付は絶対日付に直す（「先週」→「2026-07-20」）
4. 書き込みは本人の承認を得てから行う。エージェントが勝手に大量生成しない

## エージェント側メモリとの関係

エージェントが持つ作業メモリと、このリポジトリは役目が違う。同じ知見が両方にあること自体は重複ではない。

| | 持つもの | 寿命 |
|---|---|---|
| エージェントのメモリ | そのプロジェクトで起きた実例・適用手順・本人の判断 | 環境ごと・機械ごと |
| このリポジトリ | 人が採用を判断し、横断的に一般化した規則 | 環境から独立 |

昇格（メモリ → ここ）のあとは、一般化した規則だけをここに書き、メモリ側は消さずにここへのポインタを1行足す。
逆向きのリンク（ここ → メモリ）は張らない。メモリのパスは機械ごとに違う。

## 禁止事項

- 秘密情報（APIキー・トークン・パスワード）。設定例を貼るときはプレースホルダに置換する
- プロジェクト固有の事実（特定リポジトリの構造・進捗など）。それは各プロジェクトのドキュメント・メモリへ
- 会社・顧客の情報、会話ログ、個人の絶対パス

## 検査

- pre-commit で `scripts/check.py`（frontmatter・索引整合）が走る。`gitleaks` が入っていれば秘密情報も検査する
- 手動実行: `python3 scripts/check.py`
- clone 直後に1回: `git config core.hooksPath githooks`
